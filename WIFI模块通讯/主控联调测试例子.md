# 主控与 Wi-Fi 联调测试例子

给主控软件使用。报文格式以《主控与 Wi-Fi 联动协议》为准。下面的例子按当前 6461 固件实际收发编写，`id` 请换成日志里收到的数字。

一条报文是一个 UTF-8 JSON，里面不要换行，最长 1600 字节。

Wi-Fi 的 `set`、`http`、`stream` 由模组主动下发，SDIO 指示号 `0x083B`，载荷是 JSON 加结尾 0。主控收下后，用 Direct Buffer `0x003B` 回 `ack`。主控自己的 `get`、`report`、`file`、`stream state` 仍放进 `0x003B` 的 `trans`。

---

## 1. 一次交换带回什么

主控每次向 `0x003B` 的 `trans` 放入一条报文，Wi-Fi 在同一次交换里只带回这条请求自己的应答：

| 主控放入 | Wi-Fi 带回 |
| --- | --- |
| 空字符串 | 空字符串。待发的 `set`、`http`、`stream` 不从这里取出 |
| `ack` | 空字符串。`id` 与当前待确认报文相同则这条命令完成，下一条由 `0x083B` 另发 |
| `get` | 带查询结果的确认。结果就在这一条里 |
| `report`、`file`、`stream` | 这条指令自己的确认 |

两边的 `id` 各自从 1 递增，互不影响。比较时按数字，不要按字符串。

3 秒没有确认，Wi-Fi 用同一个 `id` 再发，最多 3 次。3 次都没有，Wi-Fi 重新发全量 `set`。这期间不要拆掉 SDIO。

同一条主控命令用相同 `id` 再发时，Wi-Fi 只重发上一次确认，不重复执行。

---

## 2. 建议按这个顺序测

1. 链路恢复后等 `0x083B` 上的全量 `set`，用 `0x003B` 确认。
2. 发全量 `report`。这次只带回 `report` 的确认。凭证已经就绪时，`http` 随后从 `0x083B` 下来，再确认它。
3. 再测 `get`、增量 `set`、`file`、`stream`。增量 `set` 和 `stream` 的 start/stop 也在 `0x083B`。

`file` 在 `http` 被确认之前会得到 `result` 为 2。`get` 从链路恢复起就可以发。

---

## 3. set

方向：Wi-Fi → 主控。链路恢复后的第一包是全量，包含第 3 节里除喂食以外的全部键。不含 `feed_plan_switch`、`feed_plan`、`feed_manual`。平时不含 `memory_format`。

SDIO 就绪后，Wi-Fi 从 `0x083B` 发来示例（取值以设备当前保存为准）：

```json
{"cmd":"set","id":1,"dps":{"pir_sens_level":"high","pir_detect_intv":0,"pir_record_dur":10,"squirrel_detect_switch":true,"ai_detect_switch":true,"bird_detect_switch":true,"other_detect_switch":false,"brand_wm_switch":true,"datetime_wm_switch":true,"mic_switch":false,"status_led_switch":true,"image_filter_level":"medium","image_anti_flicker":"60Hz","datetime_wm_format":"MM/dd/yyyy HH:mm:ss","spk_vol":80}}
```

主控确认：

```json
{"cmd":"ack","id":1,"result":0}
```

判定：键集合与上面一致，`id` 与确认相同。确认走 `0x003B`，这次交换的返回是空字符串。`http` 要等全量 `report` 之后才从 `0x083B` 下来。

平台把 `pir_sens_level` 改成 `low` 后，Wi-Fi 从 `0x083B` 另发只含变化键的一包，不必等 `http` 确认：

```json
{"cmd":"set","id":4,"dps":{"pir_sens_level":"low"}}
```

仍用收到的 `id` 确认，`result` 为 0。全量还没取走时，取到的就是带新值的全量。已经取走、正在等确认的那一包不改写，确认后的这一次交换带回增量。

主控暂时做不了时：

```json
{"cmd":"ack","id":1,"result":2}
```

Wi-Fi 把这一条计入重试。拒绝用 `result` 为 1，Wi-Fi 不会重发这一条。

---

## 4. report

方向：主控 → Wi-Fi。全量 `set` 确认之后发一次全量。

主控发送：

```json
{"cmd":"report","id":1,"properties":{"memory_capacity":{"total":32,"used":1.2},"memory_status":"normal","memory_format_status":"success","firmware_version":"1.0.0"}}
```

Wi-Fi 同一次交换返回：

```json
{"cmd":"ack","id":1,"result":0}
```

判定：这次只返回上面这条确认，不再把 `http` 塞进同一次交换。`used` 最多一位小数。凭证已经就绪时，`http` 接着从 `0x083B` 下来。

之后只报变化的键，例如：

```json
{"cmd":"report","id":2,"properties":{"memory_status":"unmount"}}
```

格式化过程先报 `formatting`，结束再报 `success` 或 `fail`。失败时把当时的 `memory_capacity` 和 `memory_status` 一并带上。

---

## 5. http

方向：Wi-Fi → 主控。全量 `report` 被确认并且凭证已经就绪之后，由 `0x083B` 主动下发。3 秒内没有 `ack` 会按同一个 `id` 再发，最多 3 次。

```json
{"cmd":"http","id":2,"baseUrl":"https://gateway.example","productCode":"P_SBF_F5gT8bN7","deviceSn":"D_1A18BB28B91fDq5ems6qpzy","version":"1.0.0","accessToken":"<由设备填入>","httpHmacSignKey":"<Base64>","httpAesKey":"<Base64>","expireTime":1730000000000}
```

主控确认：

```json
{"cmd":"ack","id":2,"result":0}
```

判定：`baseUrl` 末尾没有斜杠。`version` 等于主控刚报过的 `firmware_version`，还没报过则为 `1.0.0`。`expireTime` 是 13 位毫秒。没有 `refreshToken`。确认 `result` 为 0 之后才可以按协议第 6 节访问云端 HTTP。

6461 串口日志里这三个字段会显示成 `***`，发给主控的报文本身是完整值。

---

## 6. get

方向：双向。确认就是回复，不要再等另一条。下面都是主控来问 Wi-Fi。主控回答 Wi-Fi 的 `get` 时字段同协议第 5 节，当前固件还不会主动向主控发 `get`。

### 6.1 status

主控发送：

```json
{"cmd":"get","id":2,"name":"status"}
```

Wi-Fi 返回：

```json
{"cmd":"ack","id":2,"result":0,"status":{"cloud":"online","wifi_signal_level":51,"battery_level":0,"motor_status":"normal","http":"ready"}}
```

`cloud` 为 `online` 或 `offline`。`http` 为 `ready` 或 `none`。电量计未接时 `battery_level` 为 0，马达未测时 `motor_status` 为 `normal`。

### 6.2 dps

主控发送：

```json
{"cmd":"get","id":3,"name":"dps"}
```

Wi-Fi 返回的 `dps` 与第 3 节当前生效值一致，没有喂食键，也没有 `memory_format`。

```json
{"cmd":"ack","id":3,"result":0,"dps":{"pir_sens_level":"medium","pir_detect_intv":0,"pir_record_dur":10,"status_led_switch":true,"spk_vol":80}}
```

上面只列出一部分键。实包应包含全量 `set` 里的那些键。

### 6.3 http

主控发 `get`，`name` 为 `http`。Wi-Fi 向云端再要一次凭证，新凭证放在这次确认的 `http` 里。这一轮没换到则 `result` 为 2，过一会儿重发同一条 `get`。距离 `expireTime` 不足 10 分钟，或云端 HTTP 返回 401 时，就用这个 `get` 换新凭证。

换到了：

```json
{"cmd":"get","id":4,"name":"http"}
```

```json
{"cmd":"ack","id":4,"result":0,"http":{"baseUrl":"https://gateway.example","productCode":"P_SBF_F5gT8bN7","deviceSn":"D_1A18BB28B91fDq5ems6qpzy","version":"1.0.0","accessToken":"<由设备填入>","httpHmacSignKey":"<Base64>","httpAesKey":"<Base64>","expireTime":1730000000000}}
```

这一轮没换到：

```json
{"cmd":"ack","id":4,"result":2}
```


### 6.4 stream

```json
{"cmd":"get","id":5,"name":"stream"}
```

```json
{"cmd":"ack","id":5,"result":0,"stream":{"state":"idle","streamId":""}}
```

还没推流时 `state` 为 `idle`，`streamId` 为空字符串。推流确认成功后 `state` 为 `pushing`。

### 6.5 不认识的 name

```json
{"cmd":"get","id":6,"name":"other"}
```

```json
{"cmd":"ack","id":6,"result":1}
```

## 7. file

方向：主控 → Wi-Fi。每个阶段各发一条，并等待确认。Wi-Fi 只记录，不代替主控调用云端上传接口。

`http` 尚未确认时，下面任何一条都会得到 `result` 为 2。确认之后成功为 0。

准备阶段：

```json
{"cmd":"file","id":10,"phase":"prepare","purpose":"image","eventId":"0123456789abcdef","detectType":"bird","fileId":"","result":0}
```

```json
{"cmd":"ack","id":10,"result":0}
```

上传阶段把 `phase` 换成 `upload`。做完云端 `report` 后发完成。失败时这一条的 `result` 为 1，Wi-Fi 仍然确认 0，表示已经记下：

```json
{"cmd":"file","id":12,"phase":"done","purpose":"image","eventId":"0123456789abcdef","detectType":"bird","fileId":"file-1","result":1}
```

```json
{"cmd":"ack","id":12,"result":0}
```

`purpose` 为 `image`、`cloud_video` 或 `log`。日志的 `detectType` 可以不带。`phase` 只应为 `prepare`、`upload`、`done`。

会话还没建立时的返回：

```json
{"cmd":"ack","id":10,"result":2}
```

---

## 8. stream

开始和停止由云端下发，Wi-Fi 转给主控。联调这一条需要平台发 `IpcStreamStart` 或 `IpcStreamStop`。主控不要自己编一条 `start` 发给 Wi-Fi。

Wi-Fi 发来的开始：

```json
{"cmd":"stream","id":20,"action":"start","streamId":"stream-1","pushProtocol":"RTMP","pushUrl":"rtmp://example/live","channel":"ch1","profile":"main","expireTime":1730000000000}
```

已经开始推：

```json
{"cmd":"ack","id":20,"result":0}
```

摄像机还没就绪：

```json
{"cmd":"ack","id":20,"result":2}
```

不认识 `pushProtocol`，或 `pushUrl` 为空、已过期：

```json
{"cmd":"ack","id":20,"result":1}
```

停止：

```json
{"cmd":"stream","id":21,"action":"stop","streamId":"stream-1"}
```

```json
{"cmd":"ack","id":21,"result":0}
```

推流中途断开，由主控另发：

```json
{"cmd":"stream","id":7,"action":"state","streamId":"stream-1","state":"fail"}
```

```json
{"cmd":"ack","id":7,"result":0}
```

`state` 为 `pushing`、`idle` 或 `fail`。发完后再 `get`，`name` 为 `stream`，确认里的 `state` 和 `streamId` 应与这条一致。

---

### 8.1 分片 start（2026-11-10 补充）

较长 start 按协议文档的 `part` 格式从 `0x083B` 下发。完整原始报文的 ID 与各片 ID 相同，`seq` 从 0 开始，`cnt` 是片数。

1. 仅下发第一片：主控保留内容，不执行直播，不回复成功 ACK。
2. 下发剩余片：主控解开各片 `data` 的外层 JSON 转义后，按序拼成原始 start；地址、token、有效期必须与原始报文逐字节一致。
3. 收齐后由原有直播后端执行，再通过 `0x003B` 回原 ID 的 ACK；执行成功为 0，尚未就绪为 2，地址等不满足业务校验为 1，不能把“拼接成功”算作“直播成功”。
4. 同一完整片组重发、片内重发、乱序都不应改写地址；已成功确认的同 ID 报文不得重复执行。缺片 15 秒后清理，不回 ACK0；Wi-Fi 重试时重发整个片组。

主控当前支持最多 32 片、重组总长 1600 字节，`pushUrl` 上限 1400 字节。真实直播验收仍需 APP/平台下发真实可用地址；`rtsp://host/live/x?token=AAAABBBB` 只能用于本机拼接验证，不能据此判断真实开播通过。

---

## 9. ack 与异常

正常确认：

```json
{"cmd":"ack","id":1,"result":0}
```

不是 JSON，Wi-Fi 返回：

```json
{"cmd":"ack","id":0,"result":1}
```

没有 `cmd`，或 `cmd` 不是已知指令，返回 `result` 为 1，`id` 用主控带上的数字。

---

## 10. 和协议原文不一致、以本固件为准的地方

- 主控确认 `set` 之后，Wi-Fi 不会再为这几个键向云端补一条属性上报。主控不必等云端回执。
- `get` 只实现了主控询问 Wi-Fi。Wi-Fi 不会主动发 `get`。
